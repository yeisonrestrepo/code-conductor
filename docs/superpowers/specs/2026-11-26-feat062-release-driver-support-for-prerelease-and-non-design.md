# FEAT-062: Release Driver Support for Prerelease and Non-Semver Version Schemes

**Status:** Draft (pending independent review)

Source: the `[FEAT-062]` entry in `AGENT-READABLE BACKLOG.md` (PILLAR 3), the intake of issue #295. Its acceptance criteria are answered in "Acceptance Criteria" below, tagged `[E1]`-`[E6]`, one tag per clause of the entry, in the entry's order. ## Problem

The `[FEAT-035]` release driver (`scripts/release.mjs`, shipped to installed projects as `.claude/scripts/release.mjs`) takes every fact about how a project releases from its committed profile, `.claude/release-profile.json`, except one: the version scheme. The scheme is hardcoded as `MAJOR.MINOR.PATCH` in five places:

- `digest`, `check` (`prepare`, `scripts/release.mjs:369`) and `handoff` (`:774`) refuse any other `<version>` with `RELEASE_VERSION_INVALID: <v>: only MAJOR.MINOR.PATCH is supported`, the bound FEAT-035 A3 set;
- `compareVersions` (`:299-303`) compares exactly three numeric parts, and `RELEASE_VERSION_NOT_ADVANCED` (`:375`) and the last-tag pick for the `COMMIT` range (`commitLines`, `:473-482`) both use it;
- the `{version}` capture every template compiles to is `\d+\.\d+\.\d+` (`CAPTURE`, `:79`), so a `line` location, a tag or a changelog heading holding `1.2.0-rc.1` never matches;
- a `json` location must hold a `PLAIN_SEMVER` value (`:320`);
- `--init`'s detectors read only `PLAIN_SEMVER` values (`:846`, `:849`, `:839`, `:858`).

A project that ships semver prereleases (`1.2.0-rc.1`), PEP 440 versions (`1.2.0rc1`, `1.2.0.post1`) or a CalVer scheme that is not three numeric parts (`2026.11`, `2026.11.26.1`) must change how it versions before `/cc-release` will run. That is the project adapting to the role, which the owner's FEAT-035 Q1 ruling rules out.

There is a second, sharper hazard as soon as prereleases are allowed: the profile has one `publish` step. For npm, `npm publish` without `--tag` moves the `latest` dist-tag; for a GitHub Release, `gh release create` without `--prerelease` marks the release as the repository's latest. A prerelease published through the stable step becomes "latest" by accident.

## Solution

The profile gains a `scheme` field naming one of four schemes the driver implements in code: `MAJOR.MINOR.PATCH` (the default, FEAT-035's behavior byte for byte), `semver` (SemVer 2.0.0 with prereleases), `pep440` (PEP 440 public versions in normal form) and `numeric` (two or more dot-separated numbers, for CalVer). Each scheme is a fixed grammar, a fixed precedence and a fixed "is this a prerelease" test, in the driver's source; the profile names one and never supplies a pattern. Every hardcoded use above goes through the profile's scheme. A scheme that has prereleases (`semver`, `pep440`) requires a `prerelease` object in the profile, holding a separate prerelease publish step (with its dist-tag or channel) and whether a prerelease tag counts as the last release for the next stable release's commit range. A prerelease is only ever published through that step, never through the stable `publish`; for the two publish tools the driver already proposes (`npm publish`, `gh release create`), the validator refuses a prerelease step that would move `latest`. `--init` detects the scheme from the current version and the local tags, marks it `(default)` when nothing evidences it, and refuses a current version that fits no supported scheme, with the evidence.

## Design

### Choices the entry leaves open

| # | Choice | Taken | Why |
|---|---|---|---|
| S1 | How the profile names the scheme | An optional top-level key `scheme`, one of the strings `"MAJOR.MINOR.PATCH"`, `"semver"`, `"pep440"`, `"numeric"`. Absent means `"MAJOR.MINOR.PATCH"`. Any other value refuses `RELEASE_PROFILE_INVALID: scheme: must be one of MAJOR.MINOR.PATCH, semver, pep440, numeric`. `validateProfile` (`scripts/release.mjs:211-227`) gains `scheme` and `prerelease` as optional keys | Optional with a default is what keeps every FEAT-035 profile valid and unchanged (the entry's own words). A closed list of names, with grammar and precedence in code, is the entry's rejection of both alternatives: no textual comparison and no profile-supplied regex. The default's name is the entry's own spelling. |
| S2 | Which schemes are supported, and their grammar | **`MAJOR.MINOR.PATCH`**: `^(0\|[1-9]\d*)\.(0\|[1-9]\d*)\.(0\|[1-9]\d*)$`, today's `SEMVER` (`:19`), unchanged. **`semver`**: SemVer 2.0.0 §2 and §9, `MAJOR.MINOR.PATCH` optionally followed by `-` and one or more dot-separated identifiers of `[0-9A-Za-z-]`, a numeric identifier without a leading zero; **build metadata (`+…`) is refused**. **`pep440`**: a PEP 440 public version in normal form, `N(.N)*[{a\|b\|rc}N][.postN][.devN]`, every `N` without a leading zero; **no epoch (`N!`) and no local segment (`+…`)**, and a non-normalized spelling (`1.2.0-rc1`, `1.2.0RC1`, `1.2.0.beta1`, `1.02`) is refused with its reason. **`numeric`**: two or more dot-separated decimal numbers, leading zeros allowed (`2026.01`, `24.04`, `2026.11.26.1`) | These are the schemes the entry and issue #295 name: semver prereleases, PEP 440, and CalVer that is not three parts. Build metadata is refused because SemVer §10 makes it invisible to precedence, so a release differing only by it can never advance, and npm drops it on publish. Normal form only, under PEP 440, because the templates match text: two spellings of one version would render two tags. The epoch is a re-baselining act PEP 440 itself calls rare, and a local version cannot be uploaded to a public index (PEP 440, "Local version identifiers"), so neither is a release; both stay out (Out of Scope). `numeric` asks for two parts so a stray tag such as `v1` never reads as a release; it allows leading zeros because CalVer's `0M` and `0Y` use them. A CalVer string with a non-numeric suffix (`2026.11-beta`) is not covered (Out of Scope). |
| S3 | Precedence | **`MAJOR.MINOR.PATCH`**: today's `compareVersions`, unchanged. **`semver`**: SemVer §11: the three numbers numerically; a version with a prerelease ranks below the same version without one; prerelease identifiers compare left to right, numeric ones numerically, alphanumeric ones in ASCII order, a numeric identifier below an alphanumeric one, and a longer set above an equal shorter prefix. So `1.2.0-alpha < 1.2.0-alpha.1 < 1.2.0-beta < 1.2.0-rc.1 < 1.2.0-rc.10 < 1.2.0`. **`pep440`**: the key the PEP's "Summary of permitted suffixes and relative ordering" defines: the release segment compared numerically with trailing zeros ignored (`1.2 == 1.2.0`), then the pre-release (`aN < bN < rcN`, with a dev-only release `1.2.0.dev1` below every pre-release of `1.2.0`, and no pre-release above every one), then the post-release (none below any), then the dev-release (none above any). So `1.2.0.dev1 < 1.2.0a1 < 1.2.0b2 < 1.2.0rc1 < 1.2.0 < 1.2.0.post1.dev1 < 1.2.0.post1`. **`numeric`**: part by part numerically, the shorter padded with zeros (`2026.11 == 2026.11.0`, `2026.01 == 2026.1`) | Each is the scheme's own published order, which is what the entry asks for ("compares by its own precedence"). Versions equal under precedence are not an advance, so `RELEASE_VERSION_NOT_ADVANCED` catches `1.2 → 1.2.0` under `pep440` and `2026.1 → 2026.01` under `numeric`. |
| S4 | What a prerelease is | `semver`: a version with a prerelease part. `pep440`: a version with a pre-release or a dev-release segment (a post-release alone is stable, as the PEP says). `MAJOR.MINOR.PATCH` and `numeric`: never | PEP 440's own definition ("pre-releases … and development releases"); a post-release is a stable correction of a final release. |
| S5 | Where the prerelease policy lives | A top-level `prerelease` object, **required** when `scheme` is `semver` or `pep440` and **refused** for the other two (`RELEASE_PROFILE_INVALID: prerelease: required by scheme <s>` / `not allowed with scheme <s>`). Exactly two keys: `publish`, either `null` or `{ "channel", "target", "argv" }`, and `countsAsLastRelease`, a boolean. `channel` is a non-empty `[A-Za-z0-9._-]+` string; `target` follows `publish.target`'s rule (`:176-178`); `argv` is a non-empty array whose elements may use `{tag}`, `{version}`, `{notes}`, `{sha}` and `{channel}` | Required, not defaulted: a profile that can release a prerelease states, in the file the owner confirmed, where a prerelease goes. That makes "unless the owner says so" a line in the committed, reviewed profile, never a driver default. A separate step, rather than a flag the driver splices into the stable `argv`, keeps FEAT-035 C6's rule that a profile entry is data the driver renders and never edits. `{channel}` lets an argument such as `--tag {channel}` stay in step with the channel the confirmation names. `publish: null` is a project that tags prereleases but publishes only stable releases. |
| S6 | "A prerelease never becomes latest" for the two known publish tools | `validateProfile` refuses a `prerelease.publish.argv` that starts `npm publish` unless it carries `--tag` followed by `{channel}` or the literal channel (or `--tag=<that>`); and one that starts `gh release create` unless it carries `--prerelease` and no `--latest` or `--latest=true`. Both refuse `RELEASE_PROFILE_INVALID: prerelease.publish.argv: <reason>`. Any other publish program is the owner's own command, judged by the owner at confirmation, where the channel is named (S9) | These are the two publish steps `--init` proposes (`detectPublish`, `:911-921`), so the driver already knows them; checking that the dist-tag and `--prerelease` are present catches the accident the entry names, in the committed profile, before any release. The owner who wants a prerelease on `latest` under npm says so by writing `"channel": "latest"`: that is explicit, in the profile, and named at confirmation. A GitHub prerelease marked latest is not offered (Out of Scope). |
| S7 | The version capture in templates | `compile` (`:87-100`) takes the scheme. The `{version}` capture is the scheme's grammar without anchors: `MAJOR.MINOR.PATCH` keeps `(\d+\.\d+\.\d+)` byte for byte; `semver` is `(\d+\.\d+\.\d+(?:-[0-9A-Za-z-]+(?:\.[0-9A-Za-z-]+)*)?)`; `pep440` is `(\d+(?:\.\d+)*(?:(?:a\|b\|rc)\d+)?(?:\.post\d+)?(?:\.dev\d+)?)`; `numeric` is `(\d+(?:\.\d+)+)`. Under the three new schemes a captured value is then validated by the scheme, and a value that fails is no match. Every caller (`lineLocation`, `changelogAnchor`, `sectionOf`, `commitLines`, the backlog DONE judgment) passes the profile's scheme. A `json` location's value is validated by the scheme in place of `PLAIN_SEMVER` (`:320`), its refusal reading `holds no <scheme> version at HEAD` (the `MAJOR.MINOR.PATCH` text unchanged) | This is what makes the tag template, the changelog heading and the version lines "work with prereleases" (the entry): the same template matches `1.2.0` and `1.2.0-rc.1`. Validating after capture keeps the regex in the driver's source simple and the scheme's rules in one function. Not validating under `MAJOR.MINOR.PATCH` keeps its matching exactly as shipped. |
| S8 | The last release for the `COMMIT` range | `commitLines` (`:473-482`) keeps its rule (the highest local tag matching the tag template, ordered by the scheme's precedence; the whole history when none) with one filter: when `<version>` is stable and `prerelease.countsAsLastRelease` is `false`, tags whose version is a prerelease are skipped. When `<version>` is itself a prerelease, or `countsAsLastRelease` is `true`, every matching tag counts. No other change: under `MAJOR.MINOR.PATCH` a prerelease tag never matches the template (S7), so the range is the one FEAT-035 computes | The entry: "a prerelease does not count as the last release for the next stable release's range unless the profile says so". A stable `1.2.0` after `1.2.0-rc.1` and `-rc.2` then lists every commit since `1.1.0`, which is what its changelog entry describes. A prerelease's own range starts at the previous tag of any kind, so `-rc.2` lists what changed since `-rc.1`. |
| S9 | The publish step and its confirmation | `handoff` prints, for a stable `<version>`, exactly FEAT-035 C9's lines. For a prerelease: with `prerelease.publish` `null`, no `PUBLISH-TARGET` and no publish `STEP`; otherwise `PUBLISH-TARGET <prerelease.publish.target>`, then `PUBLISH-CHANNEL <channel>`, then `STEP <n> publish <prerelease.publish.argv rendered>`, `{channel}` rendering the channel. The stable `publish` argv is never printed for a prerelease. `/cc-release --handoff`'s confirmation, when a `PUBLISH-CHANNEL` line was printed, reads "this publishes to `<PUBLISH-TARGET>` on channel `<PUBLISH-CHANNEL>` and cannot be undone"; without one it reads as today | "The publish confirmation names the dist-tag or channel the release goes to" (the entry). Printing the channel as its own line, rather than parsing it out of the argv, gives the command one value to quote and the tests one line to pin. The stable path prints nothing new, so its confirmation and every existing test stay as they are. |
| S10 | What `digest` adds | Under a scheme other than `MAJOR.MINOR.PATCH`, one line after `RELEASE`: `SCHEME <scheme> <stable\|prerelease>`, the second word saying what `<version>` is. Under `MAJOR.MINOR.PATCH` (named or defaulted), no new line | The agent and the owner see which order the advance check used and which publish path `handoff` will take. Printing it only for the new schemes is what keeps "an unchanged result for every existing `MAJOR.MINOR.PATCH` profile". |
| S11 | What `--init` detects, and when it refuses | The version detectors (`detectVersions`, `jsonLocations`, `tomlLocation`, `:837-865`) read a candidate version token (`^\d[0-9A-Za-z.+!-]*$`) where they read `PLAIN_SEMVER` today, then classify. The evidence is the current version plus every local tag that is `v<token>` or `<token>`, with the prefix `detectTag` chose. Each piece of evidence is classified: a semver prerelease (`X.Y.Z-…`) evidences `semver`; a PEP 440 pre, post or dev segment evidences `pep440`; a value that is numeric but not three parts, or has a leading zero, evidences `numeric`; a plain `X.Y.Z` evidences nothing. One evidenced scheme is proposed with its evidence (`(from tag v1.2.0-rc.1)`, `(from pyproject.toml 1.2.0rc1)`); none proposes `"MAJOR.MINOR.PATCH"` marked `(default)`. Two evidenced schemes refuse `RELEASE_INIT_SCHEME_CONFLICT: <scheme> from <evidence>; <scheme> from <evidence>`. A current version that fits no supported scheme refuses `RELEASE_INIT_SCHEME_UNSUPPORTED: <path> <value>: fits none of MAJOR.MINOR.PATCH, semver, pep440, numeric` (with the scheme's own reason when one nearly fits, for instance `not in PEP 440 normal form`). A tag that fits no scheme is not evidence and is ignored. For `semver` and `pep440` the proposal also carries `prerelease`, marked `(default)`: `countsAsLastRelease: false`, and `publish` derived from the stable proposal: `npm publish --tag {channel}` with channel `next` for npm, the `gh release create …` argv plus `--prerelease` with channel `prerelease` for a GitHub Release, `null` when the stable `publish` is `null`. The proposal rows become `versions`, `scheme`, `changelog`, `tag`, `remote`, `mainline`, `checks`, `publish`, then `prerelease` when proposed | The entry: detect "from the current version and existing tags", mark `(default)` when nothing evidences it, refuse an unsupported scheme with the evidence, never guess at release time. The current version is the one fact every later verb validates, so only it can make `--init` refuse; a stray old tag the template would never match cannot block a project. A plain `1.2.0` fits every scheme, so it decides nothing. The proposed `prerelease` block is the safe answer the owner reviews before confirming (FEAT-035 C14's pattern), never a value the driver falls back to later. |
| S12 | Refusals under the new schemes | `digest`, `check` and `handoff` refuse a `<version>` the profile's scheme rejects with `RELEASE_VERSION_INVALID: <v>: not a <scheme> version: <reason>`; under `MAJOR.MINOR.PATCH` the text stays `<v>: only MAJOR.MINOR.PATCH is supported`. `RELEASE_VERSION_NOT_ADVANCED: <v> does not advance <current>` keeps its text and follows the scheme's precedence | One code per fact, as FEAT-035 has it; the reason names the rule broken, so the owner can tell `1.2.0+build` (build metadata) from `1.2.0-RC1` under `pep440` (not normal form). Keeping the default's text keeps its tests and its users' scripts unchanged. |

### `scripts/release.mjs`

- One internal table of the four schemes, each `{ name, capture, parse(text) → value or reason, compare(a, b), isPrerelease(v) }`, and one `schemeOf(profile)` returning the profile's (default `MAJOR.MINOR.PATCH`). Nothing outside the file needs it except through the exports below; `orchestrate.mjs` keeps importing only `loadProfile` and `releaseSurface` (`scripts/orchestrate.mjs:17`), which validate the new keys with everything else.
- `validateProfile` gains `scheme` and `prerelease` (S1, S5, S6). `checkTemplate` accepts `{channel}` only in `prerelease.publish.argv`. `releaseSurface` is unchanged: no new path joins the surface.
- `prepare` and `handoffContext` validate `<version>` through the scheme (S12); `compareVersions` stays exported with its current behavior for `MAJOR.MINOR.PATCH` and gains a scheme argument, defaulted, so its callers and tests keep working.
- `compile` takes the scheme (S7); `commitLines` filters per S8; `digestLines` prints `SCHEME` per S10; `stepLines` prints per S9.
- `init`'s detectors and `proposal` follow S11; `init --confirm` validates the proposal file with the same validator, so a hand-edited `scheme` or `prerelease` is judged exactly as at release time.
- The source still holds no fact of this repository (FEAT-035's rule).

## Behavior

### Main path

1. An npm project at `1.1.0` with a tag `v1.2.0-rc.1` runs `/cc-release --init`. The proposal shows `scheme: "semver" (from tag v1.2.0-rc.1)` and `prerelease: { "publish": { "channel": "next", "target": "the npm registry", "argv": ["npm", "publish", "--tag", "{channel}"] }, "countsAsLastRelease": false } (default)`. The owner confirms; the profile is written and committed.
2. `/cc-release 1.2.0-rc.2`: `digest` validates the version under `semver`, finds it above `1.1.0`, prints `SCHEME semver prerelease`, and lists the commits since `v1.2.0-rc.1`. The agent writes the version locations and a `## [1.2.0-rc.2] - <date>` entry; `check` passes.
3. After the merge, `handoff --version 1.2.0-rc.2` prints the tag and push steps for `v1.2.0-rc.2`, then `PUBLISH-TARGET the npm registry`, `PUBLISH-CHANNEL next`, `STEP 3 publish npm publish --tag next`. The confirmation reads "this publishes to `the npm registry` on channel `next` and cannot be undone". `latest` does not move.
4. `/cc-release 1.2.0`: above `1.2.0-rc.2` by precedence; `SCHEME semver stable`; the `COMMIT` lines start at `v1.1.0`, skipping both rc tags. `handoff` prints the stable `npm publish` step with no `PUBLISH-CHANNEL` line, exactly as FEAT-035 does.

### Alternative paths

- **A GitHub Release profile.** The prerelease step is the stable `gh release create {tag} --verify-tag --title {tag} --notes-file {notes}` plus `--prerelease`, channel `prerelease`; `handoff` prints it with `PUBLISH-CHANNEL prerelease`.
- **`countsAsLastRelease: true`.** The stable release's range starts at the highest tag of any kind, `v1.2.0-rc.2` in the example.
- **`prerelease.publish: null`.** A prerelease gets tag and push steps only; a stable release publishes as configured.
- **PEP 440.** `pyproject.toml` holds `version = "1.2.0rc1"`; `--init` proposes `pep440 (from pyproject.toml 1.2.0rc1)`. `1.2.0.post1` is stable and goes through the stable `publish`; `1.3.0.dev1` is a prerelease.
- **CalVer.** `VERSION` holds `2026.11`; `--init` proposes `numeric (from VERSION 2026.11)` and no `prerelease` key. `2026.11.1` and `2026.12` advance; `2026.11.0` does not.
- **An existing FEAT-035 profile.** No `scheme` key: every verb's output is byte-identical to today's. Writing `"scheme": "MAJOR.MINOR.PATCH"` explicitly gives the same output.
- **Plain versions everywhere.** `--init` proposes `"MAJOR.MINOR.PATCH" (default)`; the owner may edit the proposal to `semver` (and add the required `prerelease` block) before confirming, as with any other field.

### Error cases

- A `<version>` the scheme rejects: `RELEASE_VERSION_INVALID: <v>: not a <scheme> version: <reason>` (for example `1.2.0+build.5`: build metadata is not supported; `1.2.0-rc1` under `pep440`: not in PEP 440 normal form), exit 2. Under `MAJOR.MINOR.PATCH`: today's text.
- A version not above the current one by the scheme's precedence: `RELEASE_VERSION_NOT_ADVANCED` (`1.2.0-rc.1` after `1.2.0`; `1.2` after `1.2.0` under `pep440`).
- An unknown `scheme`, a `prerelease` missing under `semver`/`pep440` or present under the other two, a malformed `prerelease` object, a `{channel}` outside `prerelease.publish.argv`, an `npm publish` prerelease step without its `--tag`, a `gh release create` prerelease step without `--prerelease` or with `--latest`: `RELEASE_PROFILE_INVALID: <field>: <reason>`, from every verb, from `init --confirm` and from `orchestrate.mjs envelope release`.
- A `json` or `line` location whose `HEAD` value fails the scheme: `RELEASE_PROFILE_AMBIGUOUS`, as today (S7).
- `--init` with a current version that fits no scheme (`2.0.0.Final`, `1.0.0+build`, `1!2.0`): `RELEASE_INIT_SCHEME_UNSUPPORTED` naming the path and value. With evidence for two schemes: `RELEASE_INIT_SCHEME_CONFLICT` naming both. Nothing is written in either case, and no verb guesses a scheme later.

## Acceptance Criteria

- [ ] `[E1]` A profile without `scheme`, and one with `"scheme": "MAJOR.MINOR.PATCH"`, validate; `semver`, `pep440` and `numeric` validate with the `prerelease` rule of S5; any other value refuses `RELEASE_PROFILE_INVALID: scheme: …` (S1, S5).
- [ ] `[E2]` `--init` proposes `semver`, `pep440` and `numeric` each from a current version and from a tag that evidences it, with the evidence shown; proposes `"MAJOR.MINOR.PATCH" (default)` when only plain versions or nothing evidences a scheme; refuses `RELEASE_INIT_SCHEME_UNSUPPORTED` and `RELEASE_INIT_SCHEME_CONFLICT` with the evidence and writes no proposal; ignores a tag that fits no scheme (S11).
- [ ] `[E3]` `digest` validates `<version>` against each scheme (valid and invalid cases per scheme, including build metadata under `semver`, non-normal forms, epoch and local under `pep440`, a single part under `numeric`) and refuses `RELEASE_VERSION_NOT_ADVANCED` by each scheme's precedence: under `semver`, `1.2.0-rc.1 < 1.2.0`, and the precedence chains of S3 hold for `semver`, `pep440` and `numeric` (S2, S3, S12).
- [ ] `[E4]` A prerelease never takes the stable publish step: for an npm profile, `handoff` of a prerelease prints `PUBLISH-CHANNEL next` and `npm publish --tag next`; for a GitHub Release profile, the `gh release create … --prerelease` step with its channel; with `prerelease.publish: null`, no publish step. The validator refuses the npm step without `--tag` and the `gh` step without `--prerelease` or with `--latest`. `/cc-release --handoff` and its three mirrors name the channel in the publish confirmation (S5, S6, S9).
- [ ] `[E5]` Under `semver` and `pep440`, a `line` location, the tag template and the changelog heading match prerelease versions (`check` passes a prerelease release; `handoff` finds its heading and renders its tag); a stable release's `COMMIT` range skips prerelease tags when `countsAsLastRelease` is `false` and uses them when `true`; a prerelease's range starts at the previous tag of any kind (S7, S8).
- [ ] `[E6]` Every existing test in `tests/scripts/release.test.js` passes unmodified, and a new test runs `digest`, `check` and `handoff` on a `MAJOR.MINOR.PATCH` fixture with and without an explicit `scheme` key and asserts byte-identical stdout, stderr and exit codes (S10, S12).

## Out of Scope

- A PEP 440 epoch (`N!`) or local version (`+local`), SemVer build metadata, and CalVer with non-numeric parts (`2026.11-beta`): refused with their reason (S2). Each is a later item if a project needs it.
- A free-form pattern or a custom precedence in the profile: rejected by the entry.
- A GitHub prerelease marked as the repository's latest, and any check of publish programs other than `npm publish` and `gh release create` (S6).
- Promoting an already published prerelease to `latest` (`npm dist-tag add`), or deleting prerelease tags: the owner's own steps after a release.
- Choosing the next version, or which kind of release to cut: still the owner's argument (FEAT-035 C2).
- Changing this repository's profile or versioning; the SNAP contract, Guard 5 and `orchestrate.mjs`, which receive the new keys only through `loadProfile`.
- The records (`VERSION`, `CHANGELOG.md`, the backlog, memory), which the release writes.
