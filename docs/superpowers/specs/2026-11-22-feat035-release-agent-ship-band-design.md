## Problem

The Ship band (`[ARCH-009]`: Release, Docs; exit condition "Version gate OK, record parity OK, docs synced") has one seat filled. `[FEAT-036]` seated `docs` (`scripts/snap-contract.mjs:72`, `ROLE_BAND.docs = 'ship'`); nothing occupies the Release seat, and `ship_released` (`:71`) is claimed by no role.

The release ritual itself is prose, here and in every installed project. In this repository `docs/RELEASE-CLOSEOUT.md` lists eleven steps, and the ones that make a release (step 2, move five version locations with the `CHANGELOG` entry and the backlog heading flip; steps 3-4, run `tools/version-gate.mjs` and `tools/record-parity.mjs`; step 11, the ticket writeback) are executed by whoever remembers them, in whatever order. An installed project has no checklist at all.

- **Nothing confines a release commit to the release surface.** A hand-written release commit can carry any other edit. The Records guard (`tools/records-guard.mjs`) protects this repository's records from contributor PRs; it says nothing about what a release commit may hold besides them.
- **The checks are run by hand.** Here they are CI-backed (`docs/RELEASE-CLOSEOUT.md:3`), so a red one is found at the merge gate, after the release PR is open, never before the commit is written.
- **The tag and the publish handoff have no step at all.** Here `.github/workflows/publish.yml:3-5` publishes on a published GitHub Release and refuses a tag that disagrees with `package.json` (`:31-38`), but no checklist line says when to tag, which commit, or with which notes.
- **The writeback excerpt is cut by hand** (`docs/RELEASE-CLOSEOUT.md`, step 11), and the step depends on someone noticing that a ticket is bound.

`[BUG-046]` argued that the fix for prose a ritual can skip is an instrument, not a better paragraph (`tools/README.md`, "The registry of retired instruments"). This item applies that argument to the ritual as a whole, for every project the role is installed in.

## Solution

Add an eighth band role, `release`, seated in the Ship band and shipped to installed projects, and a shipped driver, `scripts/release.mjs`, that hardcodes no project fact. Every fact about how a project releases lives in a committed per-project **release profile**, `.claude/release-profile.json`: the version locations, the changelog path and heading format (or no changelog), the tag format, the project's own check commands, the publish step, and an optional backlog and ticket binding. `/cc-release --init` detects these from the project's files and existing tags, shows them, and writes the profile only after the owner confirms; every other verb refuses `RELEASE_NOT_CONFIGURED` without one, and nothing is guessed at release time.

The release then runs as three verbs. `digest` proves the tree is clean, the profile's checks are green before anything moves, and the target version advances; it prints everything the agent needs, already rendered from the profile. The `release` agent (`Read, Grep, Glob, Edit`: no shell, no `Write`) edits exactly the profile's file list. `check` judges the uncommitted diff line by line against the profile, then runs the profile's check commands in order as child processes, halting `RELEASE_HALT <name>: exit <rc>` on the first red one. `handoff`, after the release commit has merged, re-runs the checks at `HEAD`, writes the notes and the writeback excerpts, and prints the ordered `STEP` lines (tag, push, publish, then the writebacks), which `/cc-release` runs one at a time, each only after the owner confirms it.

This repository becomes one project among the rest: it commits its own profile, whose checks are `tools/version-gate.mjs` then `tools/record-parity.mjs` (both unchanged and still unshipped) and whose backlog binding carries its heading flip and DONE bullet. Adding the role is a versioned SNAP contract change: `release` exists at `v: 6` only, and every v1-v5 envelope stays byte-identical.

#### Amendments (2026-11-23)

The owner amended this spec after approving it on 2026-11-22. The approval covers the amended text; the rows each amendment rewrites are updated in place below.

- **A1, Windows checks.** A committed profile must start on every platform. On `win32` the driver resolves `argv[0]` through `PATH` and `PATHEXT` (case-insensitive env keys; `PATHEXT` default `.COM;.EXE;.BAT;.CMD`), never searching the repository root for a bare name. It runs a `.cmd` or `.bat` program through `cmd.exe /d /s /c` (`ComSpec` when set) with a command line the driver builds and escapes the way `cross-spawn` does, written with no dependency. A profile-supplied string is never a command line. Every other program, and every `argv[0]` of `node`, runs with no shell. A program that cannot be found halts `RELEASE_HALT <name>: exit 127` with the line `cannot find <argv[0]> on PATH with PATHEXT <extensions>`. Rewrites C6 (its sentence about `.cmd` shims is replaced by this rule); new criterion `[O8]`.
- **A2, No changelog.** `changelog` may be `null`. C3: `changelog` is `{ "path", "heading" }` or `null`; a `ticket` binding needs `backlog`, not a changelog. C4: with a `null` changelog there is no changelog judgment; any changelog-shaped edit is `RELEASE_OUT_OF_SCOPE`. C5: with a backlog bound and a `null` changelog, the claim check (`RELEASE_CLAIMS_MISMATCH`) does not apply, because there is no entry to claim from; the flips and DONE lines are still judged. C9: with a `null` changelog, `notes.md` holds the digest's `COMMIT` subjects, one `- <subject>` line each, and `RELEASE_NOT_RELEASED` checks the version locations only. C10: with a `null` changelog, each writeback excerpt holds the item's `ITEM` title line instead of a claim bullet. C13: the surface is the version locations, then `backlog.path` when bound. C14: no changelog file gives a proposed `"changelog": null` marked `(default)`, not `RELEASE_INIT_NO_CHANGELOG`; that code is removed from C14, the `init` verb, the error cases and `[O1]`. `digest` prints `CHANGELOG none` in place of the `CHANGELOG` line, and the agent prompt says: with `CHANGELOG none`, edit only the `LOCATION` lines and the backlog lines. New criterion `[O7]`.
- **A3, Version scheme.** `MAJOR.MINOR.PATCH` only, for this item. C2's refusal reads `RELEASE_VERSION_INVALID: <v>: only MAJOR.MINOR.PATCH is supported`. Out of Scope gains "Prerelease and non-semver version schemes: `[FEAT-062]`."

### `scripts/release.mjs` (new, shipped)

Ships with the rest of `scripts/`, deployed as `.claude/scripts/release.mjs` (`lib/installer/deploy.mjs:330`). `node:` builtins only; imports nothing from `tools/`; spawns only `git` and the profile's `checks` (argument arrays, no shell); no network; writes only under `.conductor/release/` and, on `init --confirm`, `.claude/release-profile.json`. Root = `git rev-parse --show-toplevel`. 6. Show the `RELEASE:` line, the `check` result and `git diff --stat`. On `ok`, the diff is the release commit for the owner to commit and open as the release pull request. On a failure or a halt, list each line, say the diff is left in place, and name `git checkout -- <files>` as the way to discard it.

**Handoff: `/cc-release --handoff <version> [--pr <N>]`**, after the release commit has merged and the owner has synced the local mainline ref:

1. `node "$S/release.mjs" handoff …`. A refusal or halt is printed, and the command stops.
2. Show every `STEP` line.
3. For each `STEP` line in order, ask the owner to confirm that one step; before the `publish` step the question reads "this publishes to `<PUBLISH-TARGET>` and cannot be undone". Run the confirmed step's command exactly as printed, appending and changing nothing (never `--close`), and show its output. Stop at the first non-zero exit, naming the step; an unconfirmed step stops the flow. The steps not run are listed as not run. The command never runs a command that is not a printed `STEP` line.
4. Remind the owner of the project's own steps after a release that the command does not perform.

## Behavior

### Main path

1. In a project with no profile, the owner runs `/cc-release --init`, reviews the proposal, confirms, and commits `.claude/release-profile.json`.
2. On a release branch with a clean tree, the owner runs `/cc-release 1.56.0 --items FEAT-035` (this repository, backlog bound).
3. `digest` reads the profile at `HEAD`, finds the tree clean, `1.56.0` above `1.55.0`, `[FEAT-035]`'s heading open, runs `version-gate` then `record-parity`, both green, and prints the digest.
4. `envelope release --item 1.56.0` installs a v6 envelope whose `ops.scope` is the profile's five paths.
5. The agent moves each `LOCATION`, inserts `## [1.56.0] - 2026-11-22` with a bullet starting `**[FEAT-035]**`, writes the `CLOSED` heading and the `DONE` line, and ends `RELEASE: 1.56.0 items FEAT-035` and its hand-back.
6. The envelope is cleared; `check` finds five changed paths, each in shape, the claims equal to `--items`, then both checks green, and prints `release: ok 1.56.0 items FEAT-035`.
7. The owner commits the diff and opens the release pull request; CI runs the same invariants; it merges.
8. After syncing the mainline ref, `/cc-release --handoff 1.56.0 --pr 301` prints the tag, push, publish and writeback steps; the owner confirms each in turn, the publish question naming the GitHub Release target, and the writeback closes the release.

### Alternative paths

- **A project without a backlog.** The profile has no `backlog`; the owner runs `/cc-release 2.4.0`; the digest lists `COMMIT` lines instead of items; the agent writes the version locations and the changelog entry only; `check` judges no backlog and no claims; `handoff` prints no writeback.
- **A project without a changelog (A2).** `init` proposes `"changelog": null` marked `(default)`; the digest prints `CHANGELOG none`; the agent writes the version locations (and, when a backlog is bound, the flips and DONE lines) only; `check` judges no changelog and no claims and fails any changelog edit `RELEASE_OUT_OF_SCOPE`; `handoff` writes `notes.md` from the `COMMIT` subjects and, with `ticket` bound, each writeback excerpt from the item's `ITEM` title line.
- **No publish step.** `publish` is `null`: `handoff` prints the tag and push steps only, and the flow has no irreversible-publish question.
- **Several items.** `--items FEAT-035,BUG-089`: one entry claims both, both headings flip, `handoff` prints one writeback per bound item.
- **An item without a bound ticket.** `handoff` prints `WRITEBACK-NONE <ID>`; when no item is bound, the publish step is the last step.
- **A writeback re-run.** `ticket.mjs writeback` answers `already written to …` (its own idempotency); the step exits 0.
- **A tag already created by hand.** `handoff` refuses `RELEASE_TAG_EXISTS` naming the tag; the owner finishes by hand.

### Error cases

- No profile at `HEAD` (never configured, or written and not committed): every verb and `envelope release` refuse `RELEASE_NOT_CONFIGURED` naming `/cc-release --init`.
- A profile with an unknown key, an unknown placeholder, a path outside the root, the profile path on its surface, or no checks: `RELEASE_PROFILE_INVALID <field>`; a surface over the scope cap: `RELEASE_SURFACE_TOO_WIDE`.
- `init` with a profile present: `RELEASE_PROFILE_EXISTS`; locations disagreeing on the current version: `RELEASE_INIT_VERSIONS_DISAGREE` (no changelog file is not an error: the proposal carries `"changelog": null`, A2); an ignored profile path: `RELEASE_PROFILE_IGNORED`.
- A version that is not `MAJOR.MINOR.PATCH`: `RELEASE_VERSION_INVALID: <v>: only MAJOR.MINOR.PATCH is supported` (A3).
- A check whose program cannot be found (on `win32`, through `PATH` and `PATHEXT`): `RELEASE_HALT <name>: exit 127` with `cannot find <argv[0]> on PATH with PATHEXT <extensions>` (A1).
- A red check before anything moves: `digest` halts `RELEASE_HALT <name>: exit <rc>` with its output; nothing is dispatched.
- A red check after the agent's edits: `check` halts naming it; the diff stays.
- An edit outside the surface, or to the profile: Guard 5 denies it `BAND_SCOPE_VIOLATION` and the agent stops; a change that reaches the tree anyway is `RELEASE_OUT_OF_SCOPE` or `RELEASE_PROFILE_CHANGED`.
- A manifest edit beyond its version locations, or a reformat: `RELEASE_LOCATION_SHAPE <path>`.
- A backlog edit beyond the flips and their DONE lines: `RELEASE_BACKLOG_SHAPE`; an entry whose claims differ from `--items`: `RELEASE_CLAIMS_MISMATCH`.
- A dirty tree, an unknown or closed item, `--items` without a backlog binding, a version that does not advance: the `digest` refusals, nothing dispatched.
- A live run in this session: `envelope release` refuses with the `release` message.
- `handoff` before the merge or before the sync: `RELEASE_NOT_RELEASED` or `RELEASE_NOT_ON_MAIN`.
- A step that fails (a rejected push, `TICKET_UNREACHABLE`): the flow stops at that step, naming it; the later steps are listed as not run.
