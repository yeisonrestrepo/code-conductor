# BUG-006 + FEAT-018: Bash Scan Guard and Surgical Search Enforcement

**Date:** 2026-06-11
**IDs:** BUG-006, FEAT-018
**Status:** Approved

---

## Problem

Two related defects in Pillar 1 (Context Reduction and Token Optimization):

**BUG-006 — Loose Read-Tool Filtering:** The Bash tool is unrestricted. The agent can run mass content-dump commands (`find .`, `ls -R`, `cat *.ts`, `grep -r '.*' .`) that flood the context window with megabytes of unscoped file content. The existing `pre-tool-use.sh` hook guards the `Read` tool for large files but does not intercept Bash tool calls at all.

**FEAT-018 — Surgical Search Not Enforced at Hook Level:** `skills/memory-first.md` documents the Grep → Glob → targeted-Read lookup chain, but BUG-002's implementation notes explicitly deferred hook-level enforcement to FEAT-018. The skill currently has no connection to a runtime guard, so the chain is advisory-only.

Combined impact: agents can bypass the memory-first protocol entirely by issuing a single Bash command that dumps the full repository into context.

---

## Solution

Add **Guard 3** to `pre-tool-use.sh` — a Bash-tool interceptor that pattern-matches mass-dump commands and hard-blocks them (`exit 1`) unless the full command string contains a token from the operator-managed `BASH_SCAN_ALLOWLIST` array. Extend `skills/memory-first.md` with a "Hook enforcement" section that names what Guard 3 blocks and lists the authorized alternatives, completing the FEAT-018 documentation side.

---

## Behavior

### Main path

1. Claude Code invokes the Bash tool with a command string.
2. The `PreToolUse` hook fires; `pre-tool-use.sh` is executed.
3. Guard 3 checks: is `CLAUDE_TOOL_NAME == "Bash"`? If not, skip Guard 3.
4. Guard 3 preprocesses the command string in two sequential normalization steps before any pattern evaluation:
   - **4a — Line continuation joining:** Before scanning for line continuations, normalize line endings: strip any trailing carriage return (`\r`) from each line so that CRLF (`\r\n`) and LF (`\n`) inputs are treated identically — a raw `\r` at the end of a line must not be counted as a backslash or confuse the trailing-character scan. After CRLF normalization, scan each line's trailing characters: count the number of consecutive backslashes immediately preceding the (now bare) newline. If that count is **odd**, the final backslash is a line-continuation escape — replace the entire backslash-newline sequence with a single space and join the line to the next. If the count is **even**, all backslashes are paired literal-escape sequences and the newline is a real line terminator; no joining is performed. (Example: `cmd \<CR><LF>arg` → strip `\r` → `cmd \<LF>arg` → one backslash → odd → joined to `cmd arg`; `cmd \\<CR><LF>arg` → strip `\r` → two backslashes → even → not joined; `cmd \\\<newline>arg` → three backslashes → odd → the first two form a literal `\\` and the third is the continuation.)
   - **4b — Comment stripping:** Remove everything from the first unquoted, non-backslash-escaped `#` to the next `\n` (end-of-line); the `\n` itself is preserved as a line separator. A `\#` sequence in UNQUOTED state is a literal hash and does not begin a comment (e.g., a regex argument of `\#foo` is preserved intact). **`#` inside quoted states is never a comment:** a `#` character encountered while in SINGLE_QUOTED or DOUBLE_QUOTED state is treated as a literal character and has no comment-stripping effect (e.g., `grep "#pattern" file` preserves `#pattern` as the argument; `grep '#pattern' file` likewise; only `grep #pattern file` with `#` in UNQUOTED state strips ` #pattern file`). **Tokenization strategy (pure Bash):** Use a character scanner with five states — UNQUOTED, SINGLE_QUOTED, DOUBLE_QUOTED, ANSI_C_QUOTED, LOCALE_QUOTED — implemented as a `while` loop over `${cmd:i:1}` character indices. **Backslash escape handling by state — summary table:**

| State | `\X` meaning | Exit condition |
|---|---|---|
| UNQUOTED | `\` is an escape prefix; the following character is consumed as a literal (`i += 2`); `\` prevents `'`, `"`, `#`, newline from triggering state changes | Quoted state starts on first unescaped `'` or `"` |
| SINGLE_QUOTED | `\` is **not** an escape prefix — it is a literal character with no special meaning; **any** `'` (even immediately after `\`) exits to UNQUOTED; there is no way to include a literal `'` inside single quotes | Any bare `'` |
| DOUBLE_QUOTED | `\` is an escape prefix; the following character is consumed as a literal (`i += 2`); prevents `"` from being a state-exit trigger | First unescaped `"` (i.e., `"` not immediately following `\` after `i += 2` rule) |
| ANSI_C_QUOTED | `\` is an escape prefix (`i += 2`); same as DOUBLE_QUOTED for state-tracking purposes | First bare `'` |
| LOCALE_QUOTED | `\` is an escape prefix (`i += 2`); identical to DOUBLE_QUOTED rules | First unescaped `"` |

**Critical distinction:** in SINGLE_QUOTED state, `\` is always a literal — the sequence `\'` does NOT prevent the `'` from terminating the state. In all other states that recognise `\` as an escape prefix, the `i += 2` advancement means the escaped character is never re-evaluated and cannot trigger a state transition or comment.

Rules: (a) In UNQUOTED state: a `\` causes the immediately following character to be consumed as a literal without state evaluation — advance `i += 2`; a `$` followed immediately by `'` (two-character lookahead `${cmd:i:2} == "$'"`) transitions to ANSI_C_QUOTED state and advances `i += 2` (consuming both `$` and `'`); a `$` followed immediately by `"` transitions to LOCALE_QUOTED state and advances `i += 2`; a bare `'` (not part of `$'`) transitions to SINGLE_QUOTED; a bare `"` (not part of `$"`) transitions to DOUBLE_QUOTED; a `#` not preceded by `\` begins a comment — everything from that index to the next `\n` is removed. (b) In SINGLE_QUOTED state: `\` is a regular character with no escape effect; `#` is literal; **any** `'` (regardless of what precedes it) exits back to UNQUOTED — `\'` exits SINGLE_QUOTED on the `'`. (c) In DOUBLE_QUOTED state: a `\` causes the next character to be consumed as a literal with `i += 2`; `#` is literal; a `"` not preceded by `\` (i.e., not consumed by a preceding `\` via `i += 2`) exits back to UNQUOTED. (d) In ANSI_C_QUOTED state (`$'...'`): a `\` causes the next character to be consumed as a literal with `i += 2` (recognising escape sequences such as `\n`, `\t`, `\xNN`); `#` is literal; only a bare `'` exits back to UNQUOTED. (e) In LOCALE_QUOTED state (`$"..."`): identical rules to DOUBLE_QUOTED; a `\` causes `i += 2`; `#` is literal; a `"` not preceded by `\` exits back to UNQUOTED. **Obfuscation note:** `$'cat'` in ANSI_C_QUOTED state and `$"cat"` in LOCALE_QUOTED state are both treated as opaque quoted strings by the scanner; they remain subject to the command-name obfuscation block rule (a command-position token that is a `$'...'` or `$"..."` form is blocked as a potentially obfuscated invocation). This produces the **comment-stripped string**, which is the base for all subsequent steps.
5. Guard 3 runs each blocked-pattern check against the **entire** comment-stripped string as a single continuous unit — it does not stop after the first line or first command statement. Real newlines remaining in the string after Step 4a (those not consumed by line-continuation joining) are treated as command-execution-position operators (identical to `;`), so every command statement on every line is evaluated regardless of how many lines the input spans. A multi-line Bash script submitted as a single Bash tool invocation is therefore fully covered; guard evaluation is not line-bounded. Patterns 4 and 7 (glob/multi-file expansion detection) use the three-state scanner defined in Step 4b to determine whether each expansion character (`*`, `**`, `?`, `{…}`, `[…]`) appears in UNQUOTED state — characters inside single or double quotes are not subject to shell glob expansion and must not trigger the block (e.g., `cat '*.md'` targets the literal filename `*.md` and must not be blocked; `cat *.md` expands to multiple files and must be blocked). Pattern 9 (loop keyword detection) also operates on the comment-stripped string with the three-state scanner to identify unquoted shell keywords. All patterns operate on the comment-stripped string with quotes intact. If no pattern matches, exit 0 (allow).
6. If a pattern matches, Guard 3 checks the comment-stripped command string for allowlist tokens. **Structural placement requirement:** the allowlist check is performed only within the **command segment that triggered the match** — the contiguous token sequence, bounded on both sides by command-execution-position operators (or string start/end), that contains the blocked utility invocation. A matching allowlist token found in a different command segment (e.g., in an `echo` argument later in the same string, or in a preceding safe command) is ignored and does not exempt the blocked segment. Each entry in `BASH_SCAN_ALLOWLIST` is checked as a whole token within that segment — the character immediately preceding the entry must be whitespace, `;`, `|`, `(`, `)`, `{`, `[`, `}`, `]`, `'`, `"`, or start-of-segment; the character immediately following must be whitespace, `;`, `|`, `(`, `)`, `{`, `[`, `}`, `]`, `'`, `"`, or end-of-segment. **Exception:** when the allowlist entry ends with `/`, alphanumeric characters and `_`, `-`, `.`, `/` are also permitted on the right side, because they indicate a file or subdirectory inside the allowed directory rather than a substring violation (e.g., an entry of `"docs/"` must match `docs/file.txt` and `docs/sub/page.md`). **Path traversal guard:** after a `/`-terminated match, scan the remaining path string up to the next whitespace or operator; if any path component in that string is `..` (i.e., the string contains `/../`, starts with `../`, ends with `/..`, or is exactly `..`), the allowlist match is rejected and the block proceeds — `docs/../../etc/passwd` must not be permitted through a `docs/` allowlist entry. The forward slash is **not** a delimiter on the left-side boundary check. Pure substring matching is not used.
7. If any allowlist token matches, exit 0 (allow).
8. Otherwise: print the standard block message to stderr and exit 1.

### Alternative paths

- **Allowlisted path:** If the command targets a path in `BASH_SCAN_ALLOWLIST`, the guard exits 0 and the command runs normally.
- **Non-Bash tool:** Guard 3 is skipped entirely; Guards 1 and 2 (existing) apply as before.
- **Empty or missing `CLAUDE_TOOL_INPUT`:** Guard 3 exits 0 (safe default, no false positives on empty input).
- **Chained safe + blocked command** (`ls -l && cat *.ts`, `echo ok; find . -maxdepth 2`): Guard 3 evaluates the **entire command string** as a unit. If any segment anywhere in the chain matches a blocked pattern, the entire tool invocation is blocked. The guard does not split on shell operators to evaluate segments independently — doing so would allow blocked commands to be smuggled after a safe prefix.

### Error cases

- **Comment-based bypass attempt** (`cat *.ts # docs/`): comment is stripped before allowlist check; `docs/` is never evaluated as an allowlist match.
- **Partial substring bypass** (`cat doc_files.ts` when allowlist contains `docs`): word-boundary check prevents `docs` from matching inside `doc_files`.
- **Chained safe + blocked command** (`ls -l && cat *.ts`): the entire command string is evaluated as a unit; the presence of a safe prefix does not exempt the blocked segment from triggering exit 1.
- **Backtick substitution bypass** (`` cat `ls` ``): Pattern 5 detects backtick form identically to `$(` form.
- **Agent attempts to modify `BASH_SCAN_ALLOWLIST`:** This is a strict constraint violation (see Hard Constraints). The agent must not alter the array.

## Blocked Patterns

All pattern checks run against the **comment-stripped** command string (quote normalization is pattern-specific — see step 5 of Main Path).

**Binary name word boundaries and command position:** All binary name matches (`cat`, `find`, `ls`, `grep`, `egrep`, `fgrep`, `less`, `more`, `head`, `tail`, `sed`, `awk`) must satisfy two conditions simultaneously:
1. **Word boundary** — the name must not be a substring of a longer word (e.g., `lsblk`, `concatenate`, `findall` must not trigger).
2. **Command execution position** — a token is in command execution position when it appears at the start of the command string, or immediately following a shell operator (`|`, `&&`, `||`, `&`, `;`, `;;`, `$(`, `<(`, `>(`, `` ` ``, `{`, `[`, `(`, `)`, or newline), or immediately following one of the shell keywords `then`, `else`, `elif`, `do`, or `!`. The bare `(` covers standard subshell blocks; `)` covers case-pattern closers and function-definition bodies without braces, but **only when the matching opener was a bare `(`** — see disambiguation below. The `!` keyword covers pipeline negation (e.g., `! cat *.ts` — `cat` immediately follows `!` and is in command execution position; the negation does not exempt the utility from the guard). Detection applies to the **entire path token**, not just the basename: if a path token is in command execution position and its last path component (basename) is a monitored binary, the block triggers (e.g., `/bin/cat *.ts` and `./scripts/cat *.ts` must be blocked — the full token `/bin/cat` is in command position, and its basename is `cat`). Conversely, a monitored name appearing as an intermediate path component in an argument token is not in command position and must not trigger (e.g., the `/find/` component of `grep -r x /path/to/find/results` is an argument, not a command token). **`)` disambiguation:** the scanner must maintain a lightweight parenthesis-context stack. When a `$(` or `$((` two-character sequence is seen in UNQUOTED state, push a `CMDSUBST` or `ARITH` marker respectively onto the stack; when a bare `(` is seen, push `SUBSHELL`. When a `)` is seen in UNQUOTED state: (i) if the top of the stack is `CMDSUBST` or `SUBSHELL`, pop it — the `)` closes a command substitution or subshell and does NOT itself create a new command execution position (the context after the closing `)` is already UNQUOTED and the previous operator determines position); (ii) if the top of the stack is `ARITH`, check whether the next character is also `)` — if so, pop and consume both characters as `))` closing the arithmetic expression, creating no command position; if not, pop `ARITH` and treat the single `)` as closing the arithmetic (no command position); (iii) if the stack is empty, the `)` is a bare top-level closer (case pattern or function parens) and DOES create a command execution position. Array literal `(…)` uses a bare `(` push and its closing `)` follows rule (i) — array content is never a command context.
3. **Command prefix modifiers** — a binary name also satisfies command execution position when it appears after a recognized runner prefix (`env`, `exec`, `time`, `nohup`, `coproc`, `command`, or `builtin`), with zero or more intervening tokens that are either (a) flag arguments (tokens beginning with `-` or `--`), (b) environment variable assignments, or (c) option-arguments consumed by a known option-taking flag of the current prefix modifier. **`command` and `builtin`:** neither takes any option-taking flags that consume a following token (their only flags are boolean: `-p` for `command`, `-f`/`-F`/`-b` for `builtin`); all tokens following `command`/`builtin` and their boolean flags pass directly through the prefix-modifier scan to utility detection — e.g., `command cat *.ts` and `builtin cat *.ts` both trigger Guard 3 as if `cat` were in bare command position. **VAR=val token definition** (used only within this prefix modifier scan — not applied globally to arbitrary command tokens): a token is a VAR=val assignment when it matches `^[A-Za-z_][A-Za-z_0-9]*=` as a full-prefix match — the identifier part (before `=`) consists solely of ASCII letters, digits, and underscores (i.e., valid POSIX shell variable name characters: no dots, hyphens, or slashes), and `=` appears immediately after the identifier with no intervening characters. The value portion (after `=`) is unconstrained. A token beginning with `-` or `--` is always a flag (rule a) and is never evaluated against the VAR=val pattern. A token whose identifier portion contains a `.` (e.g., `core.autocrlf=true`) is NOT a VAR=val token and is instead treated as the utility name, terminating the prefix scan. Known option-taking flags per modifier: `env` → `-u` (takes the variable name to unset); `exec` → `-a` (takes the name for argv[0]); `time` → `-o` (takes an output filename, non-POSIX); `nohup` → none; `coproc` → none. When a known option-taking flag is encountered, the immediately following token is consumed as its argument and skipped, even if that token begins with `-`. **`coproc` NAME handling:** `coproc` accepts an optional NAME before the command (e.g., `coproc READER cat *.ts`). After consuming `coproc` and any flag/assignment tokens, the scanner checks the next token: if it is not itself a monitored binary name, it is treated as the coproc NAME and skipped — the token after the NAME is then checked as the utility (e.g., `coproc cat *.ts` → `cat` immediately follows `coproc` → blocked; `coproc READER cat *.ts` → `READER` is not a monitored binary → skipped as NAME → `cat` is checked → blocked). This ensures `env -u OLD_VAR cat *.ts`, `exec -a myname cat *.ts`, `env VAR=val cat *.ts`, `coproc cat *.ts`, and `coproc READER cat *.ts` all trigger the guard as if the utility were in bare command position.

| 10 | File-slurping builtins | `mapfile -t arr < src/main.ts`, `readarray lines < *.log`, `mapfile arr < <(find . -name '*.ts')` | `mapfile` or `readarray` at any command execution position — these Bash builtins read lines from stdin (or a file redirect) directly into a shell array, slurping file content into the agent's in-memory variable space and bypassing all binary-utility checks; blocked unconditionally regardless of flags or redirect form |
| 11 | Dynamic execution primitives | `eval "cat *.ts"`, `eval "$cmd *.ts"`, `eval $(generate_cmd)`, `source dump.sh`, `. dump.sh`, `. <(cat *.ts)` | `eval`, `source`, or the dot operator (`.`) at any command execution position — all three execute external or dynamically-generated shell code whose content cannot be statically analysed; blocked unconditionally; **dot-operator disambiguation:** the standalone token `.` (exactly one period with no following `/`) at command execution position is the Bash source alias — blocked; `./script.sh` and other tokens beginning with `./` are path-invoked binaries, not the dot operator — handled by the basename rule in condition 2, not this pattern; **indirect variable dispatch** (`$cmd *.ts` where `cmd=cat`) is a known static-analysis blind spot that Guard 3 cannot detect — document this as an out-of-scope limitation; agents are expected to use direct named commands, not variable-indirection |

| 12 | Alias and function remapping | `alias c='cat'`, `alias g='grep -r'`, `alias c=cat; c *.ts` | (a) **Alias declaration:** `alias` at any command execution position followed by `NAME=VALUE` where VALUE, after stripping a single layer of surrounding quotes, starts with or equals a monitored binary name or a blocked utility name (`eval`, `source`, `.`) — block the entire command string; the alias need not be used later in the same string to be blocked; rationale: declaring an alias for a blocked utility within the same execution block is itself a bypass attempt (e.g., `alias c='cat'; c *.ts` — the `alias` declaration is blocked before the remapped call executes); (b) **Function body:** inline function definitions (`NAME() { … }`, `function NAME { … }`) do not require a dedicated rule — their bodies are parsed inline and any blocked utility inside the body is already detected by the existing patterns (e.g., `foo() { cat *.ts; }` — `cat *.ts` follows `{`, which is a command execution position operator, and Pattern 4 fires) |

**Reading/viewing utilities** (used across multiple rules): `cat`, `less`, `more`, `head`, `tail`, `sed`, `awk`, `grep`, `egrep`, `fgrep`, `mapfile`, `readarray`.

**Command-name obfuscation:** Guard 3 matches binary names against the token stream as produced by the three-state scanner; it does not evaluate shell quoting mechanics at a character-concatenation level. The following obfuscation forms are **known static-analysis limitations** (out of scope for exact detection): (a) internal quoting of individual characters (`c'a't` — shell concatenation yields `cat` at runtime but the literal token is `c'a't`); (b) per-letter backslash escaping (`\c\a\t` — each letter is an escaped literal in UNQUOTED state and the combined token is not `cat` after the `i += 2` escape rule); (c) locale-expansion form (`$"cat"` — locale string translation may yield `cat` at runtime). **Practical mitigation:** any command-execution-position token that (i) contains a `$"` prefix, (ii) consists entirely of backslash-letter pairs (e.g., `\c`, `\a`, `\t` — every character is preceded by `\` in UNQUOTED state), or (iii) contains internal single-quote boundaries that split a plain identifier (e.g., `c'a't` where the token starts and ends with unquoted letters but contains `'...'` segments) must be blocked as a potentially obfuscated invocation, even if the reconstructed name is not confirmed to be a monitored binary. An obfuscation block must produce the same exit 1 error as a pattern match, referencing the obfuscated token in the error output.

**Substitution-embedded utility detection:** `<(…)`, `>(…)`, `$(…)`, and backtick `` `…` `` all create command execution positions (listed in condition 2). Blocked utilities inside these constructs are therefore detected by all existing patterns without special handling — `sort < <(cat *.ts)` is blocked because `cat` appears after `<(` (a command execution position operator) and Pattern 4 fires on `cat *.ts`; `wc -l $(grep -r '.*' . )` is blocked because `grep` appears after `$(` and Pattern 6 fires. **Limitation:** dynamically generated command names inside substitutions (e.g., `$(echo cat) *.ts` — the literal token in the source string is `$(echo` followed by `cat)`, not `cat`) are out of scope for static detection and are not blocked by Guard 3.

**Heredoc and here-string handling:** `<<LABEL` and `<<<` are I/O redirect operators, not command-execution-position operators and not argument tokens. They must be handled as follows during pattern evaluation: (1) `<<` and `<<<` do NOT create a command execution position — the token immediately following them is not a command. (2) The heredoc label token (the bare word or quoted word after `<<`, e.g., `EOF`, `'EOF'`, `"EOF"`) is consumed as a redirect operand and must not be treated as a command, argument, or glob expression for Patterns 4, 5, 6, 7. (3) The here-string content (the token after `<<<`) is redirect input supplied to the utility's stdin; it is not a file argument and must not trigger Patterns 4, 5, or 7 (e.g., `cat <<< '*.ts'` must not block — `'*.ts'` is stdin data, not a file glob). (4) Arguments to the utility that appear **before** `<<` or `<<<` in the command token sequence are parsed normally and are subject to all pattern checks (e.g., `grep -r '.*' . <<'EOF'` is still blocked by Pattern 6 because `-r` and `'.*'` precede the redirect). (5) The body content of a heredoc is not present in the `CLAUDE_TOOL_INPUT` command string at hook-evaluation time and requires no special handling.

## Allowlist

```bash
BASH_SCAN_ALLOWLIST=()
```

- Defined as a Bash array at the top of Guard 3.
- **Default is empty.** No paths are permitted for broad scans out of the box.
- Operators add entries as needed (e.g., `"docs/"`, `".claude/"`).
- **Agents must never modify this array.** See Hard Constraints.
- **Match target:** the allowlist check (Step 6) is always performed against the **preprocessed command string** — the output of Step 4a (line-continuation joining) followed by Step 4b (comment stripping) — never the raw `CLAUDE_TOOL_INPUT` value. This closes the trailing-comment bypass vector: in `cat *.ts # docs/`, the comment ` # docs/` is stripped by the scanner in Step 4b; by the time the allowlist check executes in Step 6, the token `docs/` is not present in the evaluated string and the command is blocked. Agents cannot insert an allowlist entry via a comment.
- **Matching semantics:** Each entry is matched as an **exact literal string** — case-sensitive, byte-for-byte identical, no glob pattern expansion, no regex interpretation. The string `"docs/"` matches the token `docs/` only; it does not match `docs` (no trailing slash), `DOCS/` (wrong case), `docs/*` (glob), or any regex-like expansion. The boundary-delimiter check enforces whole-token matching: the character immediately preceding the entry must be whitespace, `;`, `|`, `(`, `)`, `{`, `[`, `}`, `]`, `'`, `"`, or start-of-string; the character immediately following must be the same set plus end-of-string (with the `/`-terminated extension described below). The forward slash is **not** a left-side delimiter. When an entry ends with `/`, the right-side boundary permits alphanumeric, `_`, `-`, `.`, `/`, `@`, and `%` (to allow files and subdirectories inside the allowed path, including scoped package paths like `@scope/module`, URL-encoded filenames containing `%`, and other standard repository path characters), but the remaining path is validated: if it contains any `..` component, the match is rejected and the command is blocked. Pure substring matching is not used; only tokens that are bounded on both sides pass.

## Acceptance Criteria

- [ ] Guard 3 fires only when `CLAUDE_TOOL_NAME == "Bash"`.
- [ ] All twelve blocked-pattern categories from the table above are intercepted and hard-blocked (exit 1).
- [ ] `mapfile` and `readarray` at any command execution position are blocked regardless of flags or redirect form (Pattern 10).
- [ ] `eval`, `source`, and the dot operator `.` (standalone, not `./path`) at any command execution position are blocked unconditionally (Pattern 11); indirect variable dispatch (`$cmd *.ts`) is documented as a known out-of-scope static-analysis limitation.
- [ ] Pattern 2 covers `-exec`, `-execdir`, `-ok`, and `-okdir`; when a shell interpreter (`sh`, `bash`, `dash`, `zsh`, `ksh`, `fish`) is the utility following any exec-family flag, the command is blocked without analysing the shell's `-c` argument.
- [ ] Pattern 3 blocks `xargs` followed by a shell interpreter in addition to reading utilities; the shell interpreter is identified using the same flag-skipping logic as for reading utilities.
- [ ] `alias NAME=VALUE` where VALUE (after stripping one layer of quotes) starts with or equals a monitored binary or blocked utility name is blocked unconditionally (Pattern 12); inline function bodies are covered by existing patterns detecting blocked utilities within the `{…}` body tokens.
- [ ] Command-execution-position tokens that are `$"`-prefixed, consist entirely of backslash-letter pairs, or contain internal single-quote segments splitting a plain identifier are blocked as potentially obfuscated invocations.
- [ ] Multi-line commands joined by trailing backslash-newline are collapsed correctly: a line ending in an **odd** number of consecutive backslashes is a continuation and is joined to the next line (backslash-newline replaced by a space); a line ending in an **even** number of backslashes is not a continuation and is left as a real line terminator (e.g., `cmd \\\<newline>arg` → odd count → joined; `cmd \\<newline>arg` → even count → not joined).
- [ ] Step 4a strips any trailing `\r` from each line before the backslash count so that CRLF line endings do not corrupt the continuation test or allow a bypass by embedding a carriage return between a trailing backslash and the newline (e.g., `cmd \<CR><LF>arg` is treated identically to `cmd \<LF>arg` — joined to `cmd arg`).
- [ ] Shell comments are stripped globally before any pattern check or allowlist evaluation; `\#` in UNQUOTED state is treated as a literal hash and does not begin a comment; a `#` inside SINGLE_QUOTED or DOUBLE_QUOTED state is a literal character and must not trigger comment stripping (e.g., `grep "#pattern" file` preserves `#pattern` intact; only `grep #pattern file` with an unquoted `#` strips the comment).
- [ ] No quote stripping is applied globally or per-pattern; the comment-stripped string retains quotes for all pattern checks; Patterns 4 and 7 use the three-state scanner to detect expansion characters only in UNQUOTED state (e.g., `cat '*.md'` is NOT blocked; `cat *.md` IS blocked).
- [ ] All binary name matches satisfy both word boundary and command execution position requirements; a binary name appearing as a path component or string argument does not trigger a block (e.g., `grep -r x /path/to/find/results` must not block on `find`); a binary name invoked via an absolute or relative path (e.g., `/bin/cat *.md`, `./cat *.md`) is treated as in command execution position — the path-invoked form triggers the guard identically to the bare name.
- [ ] Command execution position recognises `{`, `[`, `(`, `)`, backtick `` ` ``, `<(`, `>(`, `;;`, `then`, `else`, `elif`, `do`, and `!` as valid preceding operators alongside `|`, `&&`, `||`, `;`, `$(`, and newline; `)` covers case-pattern closers (`foo) cat *.ts`) and brace-less function bodies (`foo() cat *.ts`); `!` covers pipeline negation (`! cat *.ts` is blocked).
- [ ] A blocked utility preceded by `env`, `exec`, `time`, `nohup`, or `coproc` is treated as being in command execution position; intervening flags, env-var assignments, and known option-arguments are skipped before the utility name; for `coproc`, an optional NAME token (any non-monitored-binary word) is also skipped so that both `coproc cat *.ts` and `coproc READER cat *.ts` are blocked.
- [ ] The character scanner uses five states (UNQUOTED, SINGLE_QUOTED, DOUBLE_QUOTED, ANSI_C_QUOTED, LOCALE_QUOTED); `$'` in UNQUOTED state enters ANSI_C_QUOTED (exits on bare `'`); `$"` in UNQUOTED state enters LOCALE_QUOTED (exits on unescaped `"`); command-position tokens that are `$'...'` or `$"..."` forms are blocked as obfuscated invocations in addition to the existing obfuscation rules.
- [ ] Unquoted-hash detection (Step 4b) and unquoted-keyword detection (Pattern 9) both use the five-state scanner; in UNQUOTED state a leading `\` causes the next character to be consumed as a literal, preventing `\"` or `\'` from triggering erroneous state transitions.
- [ ] Patterns 4 and 7 do not block tokens where `*` or `?` are preceded by a single `\` (escaped wildcards are literals); double-backslash forms `\\*` and `\\?` do trigger the block because they represent a literal backslash followed by an active wildcard.
- [ ] Pattern 8 only fires on short-flag tokens whose full form matches `-[a-zA-Z]*R[a-zA-Z]*`; path components, parameters, and strings that merely contain the letter `R` do not trigger.
- [ ] Pattern 9 loop keywords (`for`, `while`, `until`) must satisfy both the UNQUOTED state condition and a command execution position check; bare keyword appearances as arguments or path components do not trigger.
- [ ] Pattern 3 detects `xargs` at any command execution position; option-taking flags consume the following token as their argument if and only if that token does NOT match `^-[A-Za-z]` — bare `-`, `--`, `-[0-9]+`, and non-hyphen tokens are all consumed as arguments; tokens matching `^-[A-Za-z]` are treated as the next flag and never consumed (e.g., `xargs -d - cat` → `-` consumed → `cat` blocked; `xargs -d -- cat` → `--` consumed → `cat` blocked; `xargs -d -x cat` → `-x` not consumed → `cat` blocked; boolean flags never consume a following token regardless of form).
- [ ] Pattern 5 fires on any argument token that **contains** a command substitution expression (`$(` or unquoted backtick) anywhere within it — including when the substitution is preceded by a static path prefix (e.g., `cat src/$(target_dir)/main.ts` is blocked); the exemption requires two conditions to both hold: (1) no static prefix precedes the substitution within the token, and (2) after stripping the token's **enclosing or boundary quotation marks** (the full opening and closing quotes of the shell word, not only characters adjacent to the closing `)`), the content following the substitution is a `/`-prefixed literal path with no further substitution or glob characters — both `cat "$(git rev-parse --show-toplevel)"/package.json` (separate unquoted suffix) and `cat "$(git rev-parse --show-toplevel)/package.json"` (suffix inside the same double-quoted word) satisfy this exemption and must pass through.
- [ ] Pattern 6 recursive flag is `-r`, `-R`, or `--recursive`; when `-F` or `--fixed-strings` is present, Pattern 6 does NOT fire regardless of pattern value (e.g., `grep -r -F '.*' .` passes through); Pattern 6 isolates the pattern argument via: (a) `-e`/`--regexp` forms — any match-all expression from a `-e ARG`, `--regexp ARG`, or `--regexp=ARG` fires the rule; (b) without those forms, the first non-flag, non-path-looking argument is the pattern — "path-looking" means a token that, after quote stripping, begins with `/`, `./`, `../`, or `~/`, or contains at least one `/` and no regex metacharacters; (c) `-f` (file-sourced patterns) is out of scope and must not trigger the block; `grep -r --regexp='.*' .` and `grep -r --regexp '.*' .` are both detected identically to `grep -r -e '.*' .`.
- [ ] Allowlist entries ending with `/` permit alphanumeric, `_`, `-`, `.`, `/`, `@`, and `%` characters on the right boundary, so `"docs/"` matches `docs/file.txt`, `docs/sub/page.md`, `docs/@scope/mod.ts`, and `docs/file%20name.ts` without treating them as substring violations; `..` path components in the remainder still cause the match to be rejected.
- [ ] Pattern 3 skips non-hyphen option-arguments of intermediate `xargs` flags (e.g., the `{}` replacement string after `-I`) before locating the reading utility.
- [ ] Pattern 3 treats `-i` (lowercase) as a boolean flag that consumes no following token — the optional replacement string for `-i` is attached in the same token (e.g., `-iSTR`); `-I` (uppercase) remains option-taking and consumes the next token as a mandatory separate replacement string.
- [ ] The `)` command execution position operator applies only when the parenthesis-context stack is empty (bare top-level `)` from a case pattern or brace-less function definition); `)` closing a `$(` or `$((` context does not create a command execution position; `))` closing an arithmetic `$((` expression creates no command position.
- [ ] VAR=val token detection in the prefix modifier scan requires the identifier portion to match solely `[A-Za-z_][A-Za-z_0-9]*` (no dots, hyphens, or slashes); tokens containing a `.` in the identifier part (e.g., `core.autocrlf=true`) are not treated as VAR=val assignments and are treated as the utility name.
- [ ] The path-looking definition in Pattern 6 does NOT include `.` in the disqualifying metacharacter list; tokens containing `.` (e.g., `src/main.ts`, `docs/README.md`) are path-looking; only `*`, `+`, `?`, `[`, `]`, `(`, `)`, `{`, `}`, `^`, `$`, `|`, `\` disqualify a token from being path-looking.
- [ ] The three-state scanner advances the loop index by 2 (`i += 2`) when processing a backslash escape sequence in UNQUOTED or DOUBLE_QUOTED state, ensuring the escaped character is not re-evaluated in the next iteration (e.g., `\*` costs two index positions — position of `\` and position of `*` — so `*` is never seen as a standalone expansion character).
- [ ] Pattern 1 detects depth-limiting flags in both space-separated (`-maxdepth 2`) and equals-sign (`--maxdepth=2`) forms, extracting the numeric value regardless of separator; after extraction, any leading `+` is stripped before comparing to `1` so that `-maxdepth +1` is treated as depth 1 (allowed) and `-maxdepth +2` is treated as depth 2 (blocked), preventing false positives from explicit positive-sign notation.
- [ ] `<(` and `>(` are recognised as command execution position operators, closing the process-substitution bypass vector (e.g., `while read; do cat $f; done < <(ls *.ts)` is blocked).
- [ ] Allowlist boundary delimiters include `{` and `[` on both sides of each token for symmetry with the execution-position operator set.
- [ ] Patterns 4 and 7 detect brace expansions (`{a,b}`) and bracket sets (`[abc]`) in addition to `*`, `**`, and `?`.
- [ ] For the grep family (Pattern 6), an empty or whitespace-only pattern argument after quote stripping is treated as a match-all and triggers the block.
- [ ] The block message is written to stderr; it explicitly names `skills/memory-first.md` and lists the three authorized alternatives (Grep, Glob, Read with offset+limit).
- [ ] Allowlist token matching operates on the comment-stripped string (quotes preserved) using boundary delimiters (whitespace, `;`, `|`, `(`, `)`, `}`, `]`, `'`, `"`); the forward slash is NOT a delimiter so that path-based entries like `"docs/"` match as whole tokens; pure substring matching is not used.
- [ ] Pattern 5 detects both `$(` (POSIX) and backtick (legacy) command substitution forms.
- [ ] `<<` and `<<<` are treated as redirect operators, not command execution position operators; the heredoc label token after `<<` is consumed as a redirect operand and not scanned as a command or file argument; the here-string token after `<<<` is redirect input and does not trigger Patterns 4, 5, or 7 (e.g., `cat <<< '*.ts'` must not block); arguments appearing before `<<`/`<<<` in the token sequence are scanned normally.
- [ ] `git grep` with a match-all pattern is blocked without requiring a recursive flag; `grep`/`egrep`/`fgrep` require a recursive flag in addition to a match-all pattern.
- [ ] Pattern 8 intercepts clustered short flags containing `R` (e.g., `-laR`, `-lR`) as well as standalone `-R` and `--recursive`, anchored to `ls` at command execution position.
- [ ] Guard 3 scans the entire comment-stripped string as one unit — it does not stop after the first line; real newlines act as command-execution-position operators identical to `;`, so every command on every line of a multi-line Bash invocation is evaluated.
- [ ] A Bash command string containing a blocked pattern in any segment is blocked in full, regardless of safe commands chained before or after it via `&&`, `||`, `|`, `;`, or newline.
- [ ] An empty `BASH_SCAN_ALLOWLIST` blocks all matching commands with no exceptions.
- [ ] `BASH_SCAN_ALLOWLIST` entries are matched as exact literal strings — case-sensitive, byte-for-byte, no glob expansion, no regex; `"docs/"` matches the token `docs/` only and does not match `DOCS/`, `docs`, `docs/*`, or any glob-expanded form.
- [ ] The allowlist check is confined to the command segment that triggered the blocked pattern; an allowlist token appearing in a different command segment (e.g., in an `echo` argument or a preceding safe command in the same string) does not exempt the blocked segment (e.g., `cat *.ts && echo "see docs/README.md"` — `docs/` in the echo segment does not exempt the `cat *.ts` segment).
- [ ] A non-empty `BASH_SCAN_ALLOWLIST` allows commands whose comment-stripped string contains a matching whole-token (boundary-checked) exact-literal entry.
- [ ] `BASH_SCAN_ALLOWLIST` remains `()` in the committed hook; any agent modification to this array is a constraint violation and must be caught in review.
- [ ] In SINGLE_QUOTED state the backslash `\` is a literal character with no escape effect; the sequence `\'` does NOT prevent the `'` from exiting the state — any `'` character (even immediately after `\`) terminates SINGLE_QUOTED and returns to UNQUOTED (e.g., the string `'can\'t'` tokenises as SINGLE_QUOTED `can\` → `'` exits to UNQUOTED → `t` in UNQUOTED → `'` enters SINGLE_QUOTED → empty `'` exits to UNQUOTED, not as a single token); in DOUBLE_QUOTED, ANSI_C_QUOTED, and LOCALE_QUOTED states the `i += 2` escape rule DOES prevent the escaped character from acting as a terminator.
- [ ] The `&` operator (background / async) is a command execution position delimiter; `cmd1 & cat *.ts` — `cat` immediately follows `&` and is in command execution position; the guard blocks `cat *.ts` regardless of the `&`.
- [ ] The allowlist check (Step 6) operates on the preprocessed command string (after Step 4a line-continuation joining and Step 4b comment stripping), never on the raw `CLAUDE_TOOL_INPUT` value; a trailing comment containing an allowlist token does not exempt the command (`cat *.ts # docs/` — `# docs/` stripped in Step 4b → `docs/` absent when Step 6 runs → blocked).
- [ ] A blocked utility preceded by `command` or `builtin` is treated as being in command execution position and is blocked identically to the bare-name form (e.g., `command cat *.ts` and `builtin cat *.ts` both trigger Guard 3); neither `command` nor `builtin` has option-taking flags that consume a following token — their boolean flags (`-p`, `-f`, `-F`, `-b`) are skipped and the token after them is the utility name.
- [ ] Pattern 9 fires on any `for`, `while`, or `until` at command execution position regardless of what command appears in the loop body; loops with non-reading utilities are blocked (e.g., `for f in *.ts; do wc -l $f; done` is blocked because any mass-iteration over a file set is treated as a context-flooding vector even when each individual iteration uses a permitted command).
- [ ] Guards 1 and 2 (existing large-file Read guard and duplicate-file creation guard) are unmodified.
