# FEAT-059: Security agent verdict contract with introduced versus pre-existing finding split

**Status:** Draft (pending independent review)

Source: the `[FEAT-059]` entry in `AGENT-READABLE BACKLOG.md` (PILLAR 3), the intake of issue #181. The entry's acceptance criteria are "`[FEAT-034]`'s own criteria, plus: the security verdict is read by the shared verdict parser; a test shows that a pre-existing finding never reaches the public part of the report". They are answered in "Acceptance Criteria" below: `[E1]`-`[E3]` restate FEAT-034's three criteria against the new contract, `[V1]` answers the shared parser, `[P1]` answers the public-part test, and `[S1]`-`[S3]` answer the description's "same severities", "`file:line` findings" and the split.

**Read-budget disclosure.** `/cc-spec` caps `.mjs` and `.js` reads at the first 30 lines from offset 0. This spec read `scripts/security-scan.mjs` lines 1-30 only. Every other line number cited for `scripts/orchestrate.mjs`, `scripts/security-scan.mjs`, `scripts/detect-stack.mjs` and the test files comes from Grep output (`grep -n`), not from a read past the cap. The design of FEAT-034's code is taken from its approved spec, `docs/superpowers/specs/2026-11-13-feat034-security-agent-verify-band-design.md` (cited below as "FEAT-034 C<n>"), and of FEAT-060's from `docs/superpowers/specs/2026-11-12-feat060-audit-verdict-line-and-severities-that-can-design.md`. Every source file the design touches is listed for the full read `/cc-plan` performs.

## Problem

FEAT-034 seated a `security` role in the Verify band, released in 1.48.0. Its report grammar is self-contained, and FEAT-034's own spec says FEAT-059 replaces it (FEAT-034 Out of Scope). Two things are wrong with it as the Verify band's second reviewer:

1. **The two Verify reviewers read differently.** `audit` ends in `VERDICT: APPROVE | RETURN | ESCALATE`, writes findings as `- [blocker|major|minor] <path>:<line> — …`, and is read by `parseVerdict` (`scripts/orchestrate.mjs:492-518`). `security` has no verdict line; its findings are `- [critical|high|moderate|low] <source> <location> — …` (`scripts/orchestrate.mjs:526`), where a dependency's location is `<package>@<range>` and a script's is `<path> scripts.<name>`, neither a `file:line`. It is read by its own `parseSecurityReport` (`:551`), and the router derives `blocked` from a threshold comparison (`:590-596`). An orchestrator, a reviewer or a later Ship band role must learn two formats for one band.
2. **A pre-existing vulnerability is published by the run.** `npm audit` reports every advisory in the installed tree, not only the ones the change brought in. FEAT-034 writes each one as a finding line in the agent's report, counts it on the run-file entry (`counts`), quotes the first blocking one in the `ORCH_SECURITY_BLOCKED` reason (`:602`), and the closing report names the counts. A vulnerability already present on the base branch is, by definition, present in the version the project last released. Every public artifact the run produces (its stdout, the run record `end` prints, the closing report and, once `[FEAT-035]` exists, the Ship band's PR text) then discloses it. The same holds for a credential that a change only moves: the secrets scan sees every line of a moved file as added (FEAT-034 C8 scans `git diff` added lines with no rename detection), so a key committed long ago reaches the report as a new finding.

## Solution

Put `security` on the audit's verdict contract and split its findings by origin. The agent's report becomes: an optional owner-only block of pre-existing findings, then the public finding lines (findings the change introduces), then the FEAT-034 `SCANS:` line, then exactly one `VERDICT:` line, then `SNAP_HANDBACK`. Every finding line, in either part, has the audit's form, `- [<blocker|major|minor>] <path>:<line> — …`, and carries the scan's own level and source after the dash. The severity is not the agent's choice: a level at or above the run's recorded threshold is `blocker`, below it `minor`. `handback security` cuts the owner-only block out of the report and passes the rest to the same `parseVerdict` the audit uses, so the verdict line, its placement and its count rule are checked by one function for both roles. The router then checks what it can recompute offline: the local findings against its own re-run of the base commit's scanner, which now also classifies each one as introduced or pre-existing, and the origin of each dependency finding against the base and work-tree lockfiles. The owner-only block is written to `.conductor/security-pre-existing.txt` and to nowhere else the router writes. Every public output of `handback security` (stdout, stderr, halt reasons, the run-file entry) is a function of the introduced findings and the scan statuses only, so two runs that differ only in a pre-existing finding produce the same public bytes. A pre-existing finding never changes the verdict and never blocks the run, at any level (Owner decisions, Q1). This changes released 1.48.0 behavior: 1.48.0 blocks on every dependency advisory at or above the threshold, including one already present at the base; after this item such an advisory goes to `.conductor/security-pre-existing.txt` only and the run proceeds.

### The report

```
PRE-EXISTING (owner only):
- [blocker] package-lock.json:812 — high dependency: lodash@<4.17.21; prototype pollution
END PRE-EXISTING
- [blocker] src/config.js:12 — critical secret: AWS access key id; value withheld
- [minor] package.json:7 — moderate script: scripts.test; npm test runs this changed script
SCANS: dependency=ran secrets=ran scripts=ran
VERDICT: RETURN
SNAP_HANDBACK {...}
```

- A security finding line is `- [<severity>] <path>:<line> — <level> <source>: <text>`, matched by `/^- \[(blocker|major|minor)\] (\S+:\d+) — (critical|high|moderate|low) (dependency|secret|script): \S/`. It is a valid audit finding line too (`scripts/orchestrate.mjs:494`), which is what lets `parseVerdict` count it. `<severity>` must be `blocker` when `<level>` ranks at or above `security.threshold` and `minor` otherwise (C1), else `ORCH_SECURITY_REPORT_INVALID`.
- Script text is `scripts.<name>; <sentence>`; dependency text is `<package>@<range>; <advisory title>`; secret text is `<pattern name>; value withheld` (the value is never printed, FEAT-034 D2).
- `parseSecurityReport` keeps FEAT-034's wide-candidate rule: any line beginning `- [` that is not a valid security finding, in either part, halts `ORCH_SECURITY_REPORT_INVALID`; a dependency finding when the run's dependency scan did not run halts the same (FEAT-034).

### The scanner (`scripts/security-scan.mjs`)

- **Usage.** `node security-scan.mjs <base> <threshold>`. A missing or unknown threshold is a usage error (exit 1).
- **Output.** When it found pre-existing findings, the block `PRE-EXISTING (owner only):` … `END PRE-EXISTING` first; then the introduced finding lines; then `SCAN-RESULT secrets=<ran|failed> scripts=<ran|failed>`, unchanged. Lines are in the C1/C2 form.
- **Export.** `scanChanges(root, base, threshold)` returns `{ secrets, scripts, introduced: [lines], preExisting: [lines], lockfile, changed }`, `changedPackages(root, base, lockfile)` returns the changed-package list, `'all'` or `'failed'` (`'failed'` is printed as `changed=all` and treated as `all` by step 5 of `handback security`), and the module exports `SCAN_CONTRACT = 2` (C15).
- **Lockfile line.** `LOCKFILE <path> changed=<list|none|all>` or `LOCKFILE none`, before `SCAN-RESULT` ("The agent definition" below). A lockfile that does not parse (npm) or a git failure reading the base copy makes the line `changed=all`, so every dependency finding is filed public: the failure direction keeps a finding visible and blocking rather than hiding it.
- **Classification.** A secret hit runs one `git grep -F -q -e <matched value> <base> --` from the project root; exit 0 is pre-existing, exit 1 introduced, any other exit makes the secrets scan `failed` (fail-closed, FEAT-034 C12). The value never reaches stdout or stderr. Script findings are introduced (C3).
- Everything else FEAT-034 specified (the diff, untracked files, binary skip, the base hook and the base allowlist in a temporary directory, no writes in the project) is unchanged.

### `handback security`

In this order, each step halting by name:

1. Hand-back checks as for every role (FEAT-034).
2. Split the report: find the owner-only block (C12) and cut it out, keeping each owner line's line number in the hand-back file. A malformed, repeated, unclosed or misplaced block halts `ORCH_SECURITY_REPORT_INVALID`, naming the line number only.
3. `parseVerdict(publicPart, 'security')`: `ORCH_VERDICT_MISSING`, `ORCH_VERDICT_INVALID`, `ORCH_VERDICT_INCONSISTENT` exactly as for the audit.
4. `parseSecurityReport` on both parts: finding grammar, severity mapping (C1), the `SCANS:` line immediately before the verdict (C11), the run-file consistency checks of FEAT-034, and a `failed` scan requiring `ESCALATE` (C8, `ORCH_VERDICT_INCONSISTENT`).
5. Dependency origin (C3, C4): each dependency finding's path is the lockfile the base scanner's `changedPackages` reads, its line exists, and its part matches that function's result (pre-existing exactly when the package is not in the list and the list is not `all`). A `'failed'` result is treated as `all` (the scanner's "Lockfile line" rule: a failure files every dependency finding public). A mismatch halts `ORCH_SECURITY_REPORT_INVALID: the dependency finding at .conductor/handback/security.txt:<n> is filed in the wrong part`, the same text in both directions and with no package name (C13).
6. Re-run the base scanner (FEAT-034 C17, with C15's contract check): its statuses equal the report's; each `introduced` line appears verbatim in the public part and each `preExisting` line verbatim in the owner-only block, else `ORCH_SECURITY_REPORT_INCOMPLETE`: a line the report holds in the other part gives `the local finding at .conductor/handback/security.txt:<n> is filed in the wrong part`, and a line the report holds in neither part gives `the report does not match the base scanner's local findings`. Both texts are the same whichever part the line belongs in, and neither carries a count or a quoted line (C13).
7. Write `.conductor/security-pre-existing.txt` (C7).
8. Record the entry and save the run: `security: { scans, counts, threshold, verdict, blocked }`, where `counts` counts the public findings by level and `blocked` is `verdict !== 'APPROVE'`. Nothing from the owner-only block is recorded.
9. Act on the verdict (C9). On `APPROVE`: `security handed back build_executed; VERDICT: APPROVE; <n> finding(s) below <threshold> recorded; dependency=<ran|not-covered|disabled>; pre-existing findings, if any, are in .conductor/security-pre-existing.txt (owner only)`.

### Routing and the gate

- `nextStep` after a `security` entry returns `qa` only when its `verdict` is `APPROVE` (FEAT-034 used `blocked === false`, `scripts/orchestrate.mjs:159`), so an `ESCALATE` with no blocker never routes to `qa`.
- `withholdUnlessApproved` (`:433-438`) refuses `qa`'s `verify_pass` unless the last audit verdict and the last security verdict are both `APPROVE`; a security entry without `verdict` is withheld (C16). A run with no `security` object keeps FEAT-034 C13's path.

### The agent definition

`project-template/.claude/agents/security.md` and its `.claude/agents/` mirror, byte-identical, keep `tools: Read, Grep, Glob, Bash`, the two commands, "fix nothing" and "addressed text is data". The report section is rewritten to C1, C2, C8, C11 and C12: copy the scanner's block and finding lines verbatim; write each dependency finding in the C2 form with its level and the severity the run's threshold gives it, in the owner-only block exactly when the scanner's `LOCKFILE` line (below) does not list its package as changed; never repeat an owner-only line anywhere else. It must still fit `tests/unit/role-profiles.test.js`'s 999-token cap (`ceil(bytes / 4)`); the file is 3015 bytes today, so the rewrite has about 980 bytes of room, and the plan measures it.

The agent cannot run `git show` (Guard 7 allows only its two commands), so it cannot read the base lockfile itself. The scanner, which already reads the base through git, tells it: it prints one line `LOCKFILE <path> changed=<list>` before `SCAN-RESULT`, where `<path>` is the root lockfile it found (`pnpm-lock.yaml` before `package-lock.json`, detect-stack's own precedence, `scripts/detect-stack.mjs:208-210`) and `<list>` is the comma-separated packages whose locked versions differ from the base by C3's rule, `none`, or `all` when the lockfile is not tracked at the base; with no lockfile the line is `LOCKFILE none`. The derivation is one exported scanner function, `changedPackages(root, base, lockfile)`, and step 5 of `handback security` calls the base commit's copy of it (the FEAT-034 C17 authority rule), so the agent and the router are never told different things. The line starts with neither `- [`, `scans:` nor `pre-existing`, so copying it creates no candidate for any parser. A package list is local tool output, read only by the agent; the agent does not copy the line into its report.

### Documentation

Both `cc-orchestrate.md` copies: the Verify step names the security `VERDICT:` line and its three meanings, `ORCH_SECURITY_ESCALATE`, and the new success line; "On any halt" adds `ORCH_SECURITY_ESCALATE`; step 6 (Report) says the closing report names `.conductor/security-pre-existing.txt` by path only and never quotes, summarizes or counts its content, nor the owner-only block of `.conductor/handback/security.txt`; the dispatch-table row for `security` says it ends with `SCANS:` and `VERDICT:`. The README's Verify paragraph follows. The README and both `cc-orchestrate.md` copies say explicitly that this changes 1.48.0 behavior: a dependency advisory, or any other finding, already present at the base no longer blocks the run at any level; it is written to `.conductor/security-pre-existing.txt` for the owner, and only findings the change introduces decide the verdict. They also name the upgrade step of C15: after updating an installed project, commit the updated `.claude/scripts/security-scan.mjs` before the next `start`. `tests/installer/commands-parity.test.js` keeps the two command copies in parity. The README "Known limits" lines are not touched.

## Owner decisions

The question this spec left open was decided by the project owner as follows; the design above reflects it.

- **Q1. A pre-existing finding at or above the threshold never blocks: option (a).** It never changes the verdict and never halts the run; it is written to `.conductor/security-pre-existing.txt` only. There is no `ORCH_SECURITY_PRE_EXISTING` halt. A constant halt (option (b)) was rejected because the halt itself is public and tells a reader that the released version has a vulnerability at or above the threshold, which is the disclosure this item exists to prevent, and because it would reduce `[P1]` from a byte equality to one that holds only below the threshold. This changes released 1.48.0 behavior, which blocks on pre-existing dependency advisories at or above the threshold; the Documentation section makes the README and both `cc-orchestrate.md` copies say so.
- **The spec is written against released 1.48.0.** FEAT-034 is released, so an installed 1.48.0 project meets C15's halt as its normal upgrade path and C16's `ORCH_RUN_INVALID` for a run file it wrote; both are kept, with the rationale and the reason text stated for an installed project. The line numbers this spec cites were read on branch base `4f64542` and hold on the 1.48.0 release tree `d21c418`: `git diff --stat 4f64542 d21c418` touches only `VERSION`, `package.json`, `package-lock.json`, `CHANGELOG.md`, `AGENT-READABLE BACKLOG.md`, `.claude/memory/project.md` and one README line (`:490`, the shipped agent list), none of which this spec cites by line, and no file under `scripts/`, `.claude/`, `project-template/` or `tests/` other than that memory file.

## Behavior

### Main path

1. `start` records `security.scan_command` as `node .claude/scripts/security-scan.mjs <base> high` and removes a stale `.conductor/security-pre-existing.txt`.
2. Verify runs `audit` to `APPROVE`; `nextStep` returns `security`; the agent is dispatched as in FEAT-034.
3. The agent runs `npm audit --json` and the scan command. The scanner finds no local finding and prints only `LOCKFILE package-lock.json changed=none` and `SCAN-RESULT secrets=ran scripts=ran`. `npm audit` reports `lodash` `high`. `lodash` is not listed as changed, so the agent files it in the owner-only block as `- [blocker] package-lock.json:812 — high dependency: lodash@<4.17.21; prototype pollution`.
4. The public part has no finding; the agent writes `SCANS: dependency=ran secrets=ran scripts=ran` and `VERDICT: APPROVE`.
5. `handback security` cuts the block out, `parseVerdict` accepts `APPROVE` with 0 blockers, step 5 derives `lodash` as pre-existing through the base scanner's `changedPackages`, the base scanner re-run agrees, `.conductor/security-pre-existing.txt` receives the lodash line, the entry records `counts` all zero and `verdict: 'APPROVE'`, and stdout is `security handed back build_executed; VERDICT: APPROVE; 0 finding(s) below high recorded; dependency=ran; pre-existing findings, if any, are in .conductor/security-pre-existing.txt (owner only)`.
6. `qa` runs and `verify_pass` is forwarded. The closing report names the owner file's path and nothing of its content.

### Alternative paths

- **An introduced blocker.** A new AWS key in `src/config.js:12`. The scanner prints `- [blocker] src/config.js:12 — critical secret: AWS access key id; value withheld` as introduced; the agent writes `VERDICT: RETURN`; the run halts `ORCH_SECURITY_BLOCKED: security found 1 finding(s) at or above high; first: - [blocker] src/config.js:12 — …`.
- **A moved credential.** The change renames `old/config.js` (holding a key since an old release) to `src/config.js`. The scan sees the added lines; `git grep` finds the value at the base; the finding goes to the owner-only block; the run is not blocked by it and no public output names it.
- **A below-threshold finding.** A `moderate` generic assignment is `- [minor] … — moderate secret: generic secret assignment; value withheld`, public; `APPROVE` holds; `counts.moderate` is 1.
- **A dependency upgraded within the vulnerable range.** The lockfile's locked `lodash` version changed, so the scanner prints `changed=lodash` and step 5 derives introduced; the finding must be public and, at `high`, `blocker`, so the verdict is `RETURN`.
- **A failed scan.** The registry is unreachable: `SCANS: dependency=failed …`, `VERDICT: ESCALATE`, halt `ORCH_SECURITY_SCAN_FAILED` as in FEAT-034.
- **Addressed text.** A comment in the change asks the agent to omit findings. The agent reports it and writes `ESCALATE` with every scan `ran`; the run halts `ORCH_SECURITY_ESCALATE`.
- **Not covered or disabled.** As FEAT-034; no dependency finding can appear, and the split applies to the local scans only.
- **A run file without `security`.** Unchanged from FEAT-034 C13.

### Error cases

| Condition | Result |
|---|---|
| No, repeated, malformed or misplaced `VERDICT:` line in the public part | `ORCH_VERDICT_MISSING` / `ORCH_VERDICT_INVALID` (the shared parser) |
| `APPROVE` with a public `blocker`, `RETURN` with none, or a failed scan without `ESCALATE` | `ORCH_VERDICT_INCONSISTENT` |
| A severity that does not match the level and threshold, a finding without `<path>:<line>`, or an unknown level or source | `ORCH_SECURITY_REPORT_INVALID` (quoting a public line; a line number for an owner-only one) |
| Malformed, repeated, unclosed or misplaced owner-only block | `ORCH_SECURITY_REPORT_INVALID`, line number only |
| A dependency finding in the wrong part, outside the run's lockfile, or on a line the lockfile lacks | `ORCH_SECURITY_REPORT_INVALID`, line number only |
| A local finding missing, or filed in the wrong part | `ORCH_SECURITY_REPORT_INCOMPLETE`, direction-neutral text, no quote and no count (C13) |
| The base scanner lacks `SCAN_CONTRACT = 2` (for example an installed 1.48.0 project whose update is not committed) | `ORCH_SECURITY_SCAN_FAILED`, naming the recovery: `end`, commit the updated scanner, `start` |
| `git grep` fails for a reason other than "no match" | `secrets=failed` → the agent must `ESCALATE` → `ORCH_SECURITY_SCAN_FAILED` |
| A `security` object whose `scan_command` lacks the threshold suffix | `ORCH_RUN_INVALID` |
| `qa` hands back `verify_pass` with the last security verdict not `APPROVE` or absent | `ORCH_GATE_WITHHELD` |
